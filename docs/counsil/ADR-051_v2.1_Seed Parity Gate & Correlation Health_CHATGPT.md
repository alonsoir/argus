Como revisión de fidelidad (no re-deliberación), la v2.1 me parece muy cercana a un documento listo para archivar. La arquitectura general es coherente y, más importante, el corte entre "lo que protege la correlación" y "lo que construye el engine" está mucho más limpio que en versiones anteriores.

Los únicos puntos que marcaría para validación consciente antes de ratificar son estos:

### 1. Inconsistencia menor en QUARANTINED ↔ reintegración

En §3.4 se establece correctamente:

> QUARANTINED exige confirmación binaria de divergencia de `community_id`.

Sin embargo, la reintegración automática propuesta es:

> `orphan_rate` vuelve bajo umbral durante ≥2 ventanas consecutivas.

Eso mezcla una evidencia binaria para expulsar con una evidencia estadística para readmitir.

Desde el punto de vista de máquina de estados, queda una asimetría:

```text
TRUSTED -> DEGRADED      => estadística
DEGRADED -> QUARANTINED => prueba binaria
QUARANTINED -> TRUSTED  => estadística
```

Si la filosofía es "la cuarentena requiere prueba", la salida de cuarentena probablemente debería requerir:

```text
re-gate exitoso
o
re-verificación binaria exitosa
```

El `orphan_rate` podría ser condición necesaria, pero no suficiente.

No invalida el ADR; simplemente detecto una pequeña tensión lógica interna.

---

### 2. Fase 1: "ausencia ≠ divergencia"

La regla es correcta para evitar el Catch-22.

Pero conviene dejar cristalino qué significa "ausente".

Ahora mismo pueden confundirse tres estados distintos:

| Estado          | Significado                       |
| --------------- | --------------------------------- |
| Ausente         | sensor esperado pero no participa |
| No implementado | capacidad aún inexistente         |
| Caído           | sensor debería emitir y no emite  |

La excepción introducida parece pensada para:

```text
No implementado
```

pero podría interpretarse como:

```text
Sensor muerto => WARNING
```

y eso sí sería peligroso.

Yo añadiría una frase aclaratoria del tipo:

> La excepción aplica únicamente a capacidades aún no implementadas o explícitamente excluidas de la fase; no a sensores declarados operativos que dejan de emitir inesperadamente.

---

### 3. Oracle Divergence

Esta es la decisión más delicada del ADR y, en mi opinión, la versión actual refleja correctamente lo deliberado.

La lógica es:

```text
Paridad entre sensores = requisito operativo.
Paridad con oráculo = requisito de conformidad.
```

y el sistema necesita lo primero para funcionar.

Por tanto:

```text
Nivel 1 FALSE -> fail closed
Nivel 1 TRUE + Nivel 2 FALSE -> arranque + investigación
```

me parece consistente con el objetivo del sistema.

La única condición es que el WARNING sea realmente visible y auditable, no un log perdido.

---

### 4. Split-brain runtime

Aquí veo una mejora respecto a v1.

La definición:

```text
A != B != C
```

sin mayoría reconocible,

y la caída a:

```text
observabilidad single-source
```

es probablemente la única decisión defendible.

Evita inventar un "sensor de referencia" arbitrario.

---

### 5. Corte camino crítico vs diferible

Probablemente es la parte más valiosa de toda la v2.1.

El ADR deja explícito que:

```text
Community ID gate ≠ correlation engine
```

y evita el clásico problema de pasar semanas construyendo mecanismos de resiliencia alrededor de un motor que aún no existe.

La observación:

```text
DEBT-NEO4J-FLOW-KEY-001
```

es efectivamente más estratégica para la cadena:

```text
flow
 -> graph
 -> MITRE
 -> datasets
 -> ensemble
```

que cualquiera de las DEBT operativas de este ADR.
