    Reglas de trabajo (las de siempre)

    Medir, no votar; predicción escrita antes de medir; si algo no da lo esperado, PARAR, y si una corrida falla no se sigue con el paso siguiente. Antes y después en cada paso. Comandos exactos y completos, en orden, diciendo dónde se ejecuta cada uno (Mac / defender / client), con la salida a fichero + ; cat. Ficheros generados como descarga con sha256 (se guardan desde ~/Downloads con mv). Parcheadores que validen TODO antes de escribir NADA, probados por Claude en una copia desechable; los de un solo uso no se commitean, los instrumentos de medida sí. git grep, nunca grep -rn .; inventarios sin truncar, a fichero y contados con git grep -c. awk con LC_ALL=C. El JSON es la ley. Leer el fichero entero antes de parchear. Compilar siempre el pipeline completo (make pipeline-build PROFILE=production); pruebas con make test-components PROFILE=production comprobando las cinco líneas. Las corridas del lab con DIA=dayNNN (el validador exige ^day[0-9]{3}$). Las tareas del Makefile no duplicadas se quedan. No se mantiene código deprecado. Las secciones de un documento escritas antes de medir no se reescriben. PROMPT_CONTINUE_CLAUDE.md nunca se commitea.

    Lecciones de DAY310

    • Antes de una hipótesis sobre una cuenta, leer el código que cuenta (H1 y H3 cayeron sin haberlo leído).
    • Cada corrida se nombra por lo que cambió: p2/p3 son pasos de la rama (binarios distintos), no fases.
    • Una decisión de seguridad se contrasta con el código de lo que la sostiene: F1 supone un etcd-server que autentica, y hoy no autentica.
    • Recuentos con git grep -c, no con cut -d:. Antes de borrar, quién compila además de quién llama. Antes de inventar un parámetro, leer su validador. Una predicción de git status lleva su premisa.
    • Las sesiones que pasan de la noche al amanecer acaban con comandos en la máquina equivocada: las decisiones de diseño, mejor con la cabeza fresca.
